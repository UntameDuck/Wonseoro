# 프로덕션 점검 — 하드코딩·기본값·인가

> 2026-09-23. 기능은 도는데 운영에 올릴 수 없는 코드를 찾아내고 고친 기록.
> 관련: 불일치 대장 D-27·D-28, `01-notion-sync-protocol.md`

## 왜 따로 남기는가

데모가 도는 것과 운영에 올릴 수 있는 것은 다른 문제다. 개발 편의로 넣은
기본값은 **없어도 도는 코드**를 만들고, 그 코드는 설정이 빠진 것을 알려주지 않는다.
마감 직전에 Pod 가 뜨고 첫 지원자가 500 을 받는 식으로 드러난다.

여기서 고친 것은 기능이 아니라 **틀렸을 때 어떻게 드러나는가**다.

## 1. 인가가 없었다 (D-28)

가장 심각했다. `x-applicant-id` 는 감사 기록의 actor 로만 쓰였고,
**어느 경로에서도 소유권을 확인하지 않았다.**

```
GET   /applications/{id}            남의 자기소개서를 읽는다
PATCH /applications/{id}            남의 자기소개서를 덮어쓴다
DELETE /documents/{id}              남의 서류를 마감 직전에 지운다
POST  /applications/{id}/finalize   남의 원서를 마음대로 접수시킨다
```

OpenAPI 계약만 보면 잡히지 않는다. 계약은 `security: [{ oidc: [] }]` 로
**인증**을 규정하지만 **인가**는 규정하지 않는다. 인증만 붙이면
로그인한 지원자 전원이 서로의 원서를 보게 된다.

`Ownership` 서비스를 두고 자원마다 소유자를 확인한다.
없는 자원과 남의 자원은 **같은 응답**이다 — 구분해 주면
식별자를 훑어 유효한 원서를 찾아낼 수 있다.

## 2. 중앙 Dashboard 가 전체를 돌려주고 있었다 (D-27)

`applicantToken` 파라미터를 받아놓고 `void` 로 버린 뒤 전체 100건을 반환했다.
인증을 붙여도 막히지 않는 경로였다.

중앙 요약에는 지원자를 가리키는 값이 아예 없었다. §A3 의 "최소 정보" 원칙 때문에
의도적으로 뺀 것으로 보이는데, 그러면 "내 원서" 기능이 성립하지 않는다.
`sha256(subject_token)` 을 보내기로 했다 — 원문이 아니라 해시이고,
대학별 소금을 섞지 않아 같은 사람이면 대학이 달라도 같은 값이 나온다.

## 3. 기본값이 비밀을 덮고 있었다

```
S3_SECRET_KEY  ?? 'wonseoro123'     소스에 있는 비밀키는 비밀이 아니다
AUDIT_IP_SALT  ?? 'dev-salt'        IPv4 전체를 해시해 대조하면 몇 초면 원본이 나온다
CENTRAL_ID_SALT?? 'dev-salt'        중앙이 대학 내부 식별자를 역산할 수 있다
UNIVERSITY_ID  ?? 'UNKNOWN'         여러 대학이 같은 CloudEvents source 로 보낸다
```

마지막 것이 특히 조용하다. `source` 는 중앙의 중복 제거 키의 일부다.
틀리면 중복 제거와 순서 보장이 **함께** 깨지는데, 로그에는 아무것도 남지 않는다.

`packages/server-kit/src/env.ts` 에 설정 계약을 두고,
운영에서는 기본값 자체를 금지한다. 각 서비스는 `config.ts` 에서
기동 시점에 값을 확정하고, `assertConfigured()` 가 문제를 **한 번에** 보여준다.

```
ConfigError: 설정이 올바르지 않아 기동할 수 없습니다.
  - AUDIT_IP_SALT 가 필요합니다 — 감사 로그 IP 가명처리 소금
  - CENTRAL_ID_SALT 가 필요합니다 — 중앙 전달용 식별자 가명처리 소금
  - 지원자 인증에 흉내 구현(dev-headers)을 운영에서 쓸 수 없습니다
  - ADMIN_API_TOKEN 가 필요합니다 — /admin/v1 접근 비밀. 이 뒤에 마감시각 변경과 지원자 PII 열람이 있다
  - 결제에 흉내 구현(mock)을 운영에서 쓸 수 없습니다
```

하나씩 고치며 다섯 번 재기동하게 만들지 않는다.

## 4. 흉내 구현이 운영에 섞일 수 있었다

Mock PG 는 돈을 받지 않고 받았다고 기록한다.
Mock 검사기는 아무것도 검사하지 않고 안전하다고 기록한다.
둘 다 **그 기록을 믿고 다음 단계가 진행된다.**

기능이 없는 것보다 있는 척하는 것이 위험하다.
`PAYMENT_PROVIDER` · `SCANNER_ENGINE` · `AUTH_MODE` 를 명시적 선택지로 만들고,
운영에서 흉내 구현이 골라지면 기동을 막는다. 조용히 바꿔주지 않는다 —
몰래 꺼주면 운영자는 그게 켜져 있다고 믿은 채로 다른 판단을 한다.

## 5. 운영 API 가 열려 있었다

`/admin/v1` 뒤에는 마감시각 변경, 설정 활성화, 지원자 PII 열람, 불일치 해소가 있다.
인증은 M5(T-M5-10)인데, 그때까지 네트워크가 닿는 누구나 헤더 한 줄로 마감을 바꿀 수 있었다.

`AdminGuard` 로 공유 비밀 문을 만들었다. 이것은 인증이 아니다 —
비밀 하나라 누가 했는지 구분하지 못한다. 그래서 감사에는 `x-admin-id` 를 계속 남긴다.
**문과 기록은 다른 문제다.**

## 6. 화면이 전형을 박아두고 있었다

접수 홈이 전형·모집단위 UUID 를 상수로 들고 있었다.
§A5 의 "새 전형 추가에 code fork 0" 이 화면에서 깨지는 자리다 —
대학이 전형을 하나 늘릴 때마다 프론트를 고쳐 다시 배포해야 한다.

카탈로그 API 는 이미 있었고 쓰이지 않았다. 지금은 읽어서 선택지로 그린다.

## 남은 것

- `AUTH_MODE=gateway` 의 실제 게이트웨이는 T-M5-02. 지금은 헤더 규약만 정의돼 있다
- `ADMIN_API_TOKEN` 은 임시 문이다. OIDC + MFA 는 T-M5-10
- 실 PG 연동 T-M5-06, 실 안티바이러스 T-M5-08
- D-27 의 중앙 가명 식별자 결정은 노션 §A3 과 함께 재검토가 필요하다
