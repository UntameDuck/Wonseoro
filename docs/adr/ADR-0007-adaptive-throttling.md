# ADR-0007 — 지원자 단위 Adaptive Throttling, 상태는 Pod 메모리

- 상태: 채택
- 날짜: 2026-09-30
- 관련: T-M4-40, D-51, 기술설계서 v1.1 §01 B6·A13·§06, v1.0 §8.4, STRIDE D-02

## 맥락

한 고등학교 전체가 같은 공인 IP 로 나온다. IP 로 요청을 세면 마감 직전 정상 수험생이 학교 단위로 막힌다.
설계는 "IP 단독 rate-limit 금지, session/account/application 위험점수 기반 Adaptive Throttling, CAPTCHA 는
고위험 요청에만 접근 가능한 대체수단과 함께"(§01 B6), "최종제출은 정상 세션을 과도하게 차단하지 않도록 별도
정책"(v1.0 §8.4)을 요구한다. 이 결정 전에는 앱에 요청 한도가 전혀 없었다.

## 결정

1. **키는 인증된 지원자다.** IP 는 어디에도 쓰지 않는다. 신원이 없는 요청은 인증 계층이 거절하므로 보지 않는다.
   익명 공개 조회(카탈로그·서버 시각)와 헬스·관리자·내부·PG 콜백 경로는 이 계층 밖이다 — 대량 공격은 Edge/WAF(v1.0 §8.1).
2. **요청 종류별 토큰 버킷**(지원자 × 조회·저장·생성·서류·결제·취소). 크기는 사람의 정상 속도보다 넉넉하다 —
   자동저장 3~5초 간격(0.2~0.33/s)에 저장 버킷 0.5/s·30 버스트.
3. **위험점수 0~100**, 반감기 5분. 올리는 신호: 소유권 검사 실패(남의 원서 탐색) +10, 10분 안에 전형 수(6)를 넘는
   원서를 건드림 +20, 한도 초과 +5. "아직 접수증 없음" 같은 정상 404 는 신호가 아니다 — 그래서 응답 코드가 아니라
   소유권 검사가 직접 알린다. 점수 30 이상이면 충전 속도를 절반으로, 70 이상이면 변경 요청을 멈춘다(조회는 계속).
4. **최종제출은 정상 세션에서 막지 않는다.** 점수 70 이상일 때만 넉넉한 별도 한도(5, 10초에 1)를 둔다 — Finalize 는
   멱등이라 재시도가 중복 접수가 되지 않는다.
5. 거절은 `429 RATE_LIMITED` + `Retry-After`. `THROTTLE_MODE=enforce|observe|off` — 운영 첫 적용은 observe 로
   판정만 세고(`throttle_decisions` 지표) 한도를 확인한 뒤 enforce 로 바꾼다.
6. **상태는 Pod 메모리에 둔다.** Redis(설계상 "Rate-limit 보조")를 쓰면 여러 Pod 가 한도를 공유하지만 접수 경로에
   새 의존성이 생긴다. Redis 가 느리거나 끊기면 한도 계층이 접수를 막거나, fail-open 해야 한다. Pod 가 N 개면 한 지원자의
   실효 한도가 최대 N 배가 되는 것을 받아들이고 한도를 정했다. 추적 지원자 수에 상한(10만)을 두어 메모리를 묶는다.

## 결과

- 로컬 축소 환경(kind, 단일 출발지 = NAT)에서 정상 지원자 200명 + 봇 5개를 90초 동시에 돌려 정상 사용자 429 가
  한 번도 나오지 않았고 봇 요청의 약 85% 가 거절됐다 — `tests/m4/results/nat-bot-kind-*.json`.
- 이 시험에서 **멱등 기록 실패가 처리되지 않은 Promise 거부로 API 프로세스를 죽이는 결함**을 찾아 고쳤다. DB 풀 포화는
  500 이 아니라 503 재시도 안내로 바꿨다.
- **CAPTCHA 대체 확인 수단은 아직 없다.** 위험 차단은 Retry-After 로 시간이 지나면 풀린다. 사람이 확인해서 바로 풀어 주는
  경로(접근 가능한 대체수단 포함)는 지원자 인증 연동(M5)과 함께 붙인다.
  → 2026-10-01 **ADR-0009**: 퍼즐형 CAPTCHA 는 두지 않는다. 화면이 다시 누를 시각·요청번호를 알리고 그때 버튼을 연다(T-M5-46).
  바로 푸는 길은 본인확인 다시 하기(T-M5-02).
- OpenAPI 계약에 429 응답이 없다 — 계약 파일 변경은 노션 §03 첨부 교체가 따라야 해서 D-51 로 올렸다.
- dev-headers 인증에서는 봇이 신원을 바꿔 가며 한도를 피할 수 있다. 운영(gateway)에서는 검증된 계정이 키라서 그렇지 않다.
